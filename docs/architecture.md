# Architecture

Kotlin Multiplatform with Compose Multiplatform, Material 3, MVVM and manual
dependency injection (one readable `AppGraph`, no Hilt). One codebase draws
both apps. The platforms fork only at named seams, and each platform service
is "one contract, two native twins", the pattern open-frame uses in React
Native. Everything lives under `io.raylytics.justmyweather`.

## Modules

| Module | What it is |
|---|---|
| `shared/` | The app. `commonMain` holds every screen (except Android's widget-configure screen), ViewModel, repository, the pure logic and the string catalog, and runs on both platforms. `androidMain` and `iosMain` hold the `actual`s and the Kotlin twins (OkHttp vs `NSURLSession`, the gazetteer loader, region signals, formatting). Tests: `commonTest` (both platforms) and `androidHostTest` (JVM). |
| `app/` | The Android host. `MainActivity` and `AppContainer` (`JustMyWeatherApp.kt`), plus what only Android has or does its own way: ads and consent, Play Billing, WorkManager, notifications, location, widgets, Gadgetbridge. |
| `iosApp/` | The iOS host, generated by XcodeGen from `iosApp/project.yml` (the `.xcodeproj` is not committed). A SwiftUI app (`App/JustMyWeatherApp.swift`) that shows the shared UI, plus the Swift twins in `JustMyWeather/Platform/`, one per Android service and named after it. |

`docs/PARITY.md` lists every place the platforms run different code, and
why.

## How each app starts

- **The graph.** `AppGraph` (commonMain) is the platform-neutral wiring:
  every repository, the weather clients, the location resolver, the region,
  the alert check and Remove Ads, built in one place in plain sight. Its
  constructor takes what only a platform can make: the HTTP transports, the
  settings DataStore, the gazetteer loader, the location source, the region
  signals, the billing gateway and how a notification is posted.
- **Android.** `AppContainer` extends `AppGraph` with Android's pieces and
  its Android-only extras (widgets, Gadgetbridge, the consent SDK).
  `MainActivity` is the host: it builds the ViewModels through the
  Activity's ViewModelStore, owns permissions and the system bars, and draws
  `AppRoot`.
- **iOS.** `IosApp` (iosMain) does what `MainActivity` and `AppContainer` do
  on Android. The Swift host creates it once at launch with an
  `IosPlatform` (the Swift twins), and it builds the same `AppGraph`, builds
  the ViewModels once for the app's life (iOS has no configuration changes
  to survive), and serves the UI as a `ComposeUIViewController`, plus one
  background alert check for `BGAppRefreshTask`. `IosBridges.kt` defines the
  callback-shaped protocols the Swift twins implement (`StoreBridge`,
  `AdsBridge`, `IosPlatform`), so Swift needs no Kotlin coroutines.
- **The window.** `AppRoot` (commonMain) is the window both apps draw: the
  user's theme, the app-painted background edge to edge, safe-area padding,
  the region's conventions as `LocalConventions`, and `App()` inside. `App`
  (`ui/App.kt`) is the navigation, a plain enum and a state switch. The host
  passes in what only it knows: whether ads may run, the banner as a
  composable slot, the version line, and the platform actions
  (`SupportHost`, rate, privacy choices, buy).

## The seams

Every platform difference goes through one of these. Where the Android side
existed before the port, it is the shipped code with its body unchanged; the
port only gave it a common contract to implement.

| Seam (commonMain) | Kind | Android | iOS |
|---|---|---|---|
| `data/nws/HttpTransport` | interface | `OkHttpTransport` | `UrlSessionTransport` |
| `location/LocationSource` | interface | `LocationProvider` (LocationManager, coarse) | `LocationService.swift` (CoreLocation, reduced accuracy) |
| `region/RegionSignals` | interface | `AndroidRegionSignals` (mobile network, fix, place, language) | `IosRegionSignals` (storefront, fix, place, Region setting, time zone) |
| `billing/BillingGateway` | interface | `PlayBillingGateway` | `StoreKitGateway` over `StoreService.swift` (StoreKit 2) |
| `billing/PurchaseHost` | `expect open class` | `Activity` | `UIViewController` |
| `alerts/AlertNotifications` | interface | `AlertNotifier` | `Notifier.swift` |
| `ui/SupportHost` (in `ui/App.kt`) | interface | `SupportIntents` (Build facts, own logcat, `ACTION_SENDTO`) | `SupportService.swift` (OSLogStore, Mail) |
| `view/TimeFormat` | `expect fun` | `java.time` `DateTimeFormatter`, `String.format(Locale.US)` | `NSDateFormatter` (`en_US_POSIX`), `NSNumberFormatter` |
| `region/CountryLocale` | `expect fun` | `java.util.Locale` + `java.time` | `NSLocale` + `NSDateFormatter` |
| `data/places/TextFold` | `expect fun` | `java.text.Normalizer` | `NSString` canonical decomposition |
| `ui/TestTags` `exposeTestTags()` | `expect fun` | test tags as resource ids, for Maestro and Espresso | no-op: iOS already exposes `testTag` as the accessibility id |
| `ui/theme/SansFamily` `sansFamily()` | `expect fun` | the system sans (Roboto) | bundled Roboto (SF Pro sets wider and the glance truncated) |
| `Platform.kt` `currentPlatform` | `expect val` | `ANDROID` | `IOS` |

Two things are deliberately **not** seams:

- **Ads consent** stays a per-platform twin, outside the shared code:
  `ads/AdsConsent` + `UmpConsentGateway` + `AdBanner` on Android,
  `AdsService.swift` (UMP, then Apple's tracking prompt) on iOS. The shared
  UI only sees `canShowAds` and `privacyOptionsRequired`. The two consent
  flows differ too much for one class to fit both.
- **When the alert check runs.** The check is common (`alerts/AlertCheck`,
  `AlertWorker`'s old body). Its scheduling is each platform's: WorkManager
  on Android, `BGAppRefreshTask` on iOS (`AlertRefresh.swift`), which iOS
  runs when it chooses. That is why the Alerts screen says alerts are best
  effort on iPhone (`alerts/BackgroundAlerts`).

Storage needs no seam: androidx DataStore's preferences-core is itself
multiplatform, so the repositories are common code with the same keys and
the same file format. `PreferencesCompatibilityTest` holds Android's stored
settings to byte-for-byte compatibility.

## Strings

Every word a screen draws is in one catalog,
`shared/src/commonMain/composeResources/values/strings.xml`, read as
`Res.string.*` on both platforms, so a translation is written once. Where a
sentence names the store, it has an `_ios` twin ("App Store", "Apple
Account") chosen at runtime. Copy built outside composition (ViewModel
messages, enum labels, observation ages) is still in code
(just-my-weather-nyt.12). `StringCatalogTest` checks the catalog's escapes
and placeholders: Compose resources show a backslash for a `\'` escape, so
quotes are written plainly.

## Data flow

```
HomeViewModel ─┐
CustomizeVM    ├─▶ repositories ─▶ WeatherRepository ─▶ NwsClient ─▶ HttpTransport ─▶ api.weather.gov
AlertsVM       ┘     (DataStore)        (the one seam)     (parse/retry)   (OkHttp / NSURLSession)
ThemeVM

AlertCheck (background: AlertWorker on Android, BGAppRefreshTask on iOS)
   ─▶ WeatherRepository + AlertEvaluator ─▶ AlertNotifications
```

The UI depends on exactly one domain object, `WeatherSnapshot`; the NWS wire
shapes never leak past `WeatherRepository`.

## Packages

Paths are under `shared/src/commonMain/kotlin/io/raylytics/justmyweather/`
unless marked **(app)** (Android only, under `app/src/main/java/…`) or named
as an iOS file.

- **`data/nws/`** — the weather backbone, ported from a reference TypeScript
  client. `NwsClient` talks to the free public NWS API (no key); `HttpTransport`
  is a fun-interface seam isolating the HTTP call so the retry/parse logic is
  unit-tested with a fake (no network). `Units` holds pure conversions; `NwsWire`
  is the raw JSON DTOs, `NwsModels` the cleaned-up domain shapes.
- **`data/metno/`** — the second source. `MetNoClient` (MET Norway's
  Locationforecast, CC BY 4.0, commercial use allowed) over the same
  `HttpTransport` seam, with its own small HTTP cache (OkHttp's disk cache
  on Android, an `NSURLCache` on iOS), since MET asks clients to honour
  Expires / If-Modified-Since. In NWS territory it adds
  Daily days eight and nine; everywhere else `WeatherRepository` routes every
  load to it — a "now" reading from the current forecast hour (marked
  `fromForecast`, so it never reads as "Observed"), the hourly head, and
  whole days. The verdict "not NWS territory" (an NWS `/points` 404
  InvalidPoint, and nothing less certain) is cached with the point.
- **`data/`** — `WeatherRepository` is the single seam between NWS (and the
  extended source) and the app
  (cached point resolution, label fill, current + forecast loads). The
  `*Repository` classes persist config via Preferences DataStore; `PointCache`
  (in-memory default, `DataStorePointCache` durable) survives the grid lookup
  across launches. `WeatherSnapshot` / `WeatherLocation` are the domain objects.
- **`ads/`** (app) — the one banner, on Android. iOS has its own twin,
  `iosApp/JustMyWeather/Platform/AdsService.swift`. `AdPolicy` is the pure rules (no
  personalization override — the SDK applies the user's consent — sample
  units in debug, nothing about the user in a request);
  `AdBanner` is the single composable that draws an AdMob adaptive banner. It
  is placed once, at the foot of the glance, and only while Remove Ads is not
  owned.
- **`billing/`** — the $0.99 Remove Ads purchase. `BillingGateway` is the seam
  (plain `PurchaseRecord`/`ProductOffer` values, a `BillingEvent` flow);
  `PlayBillingGateway` (app) is the only file that imports Play Billing,
  and `StoreKitGateway` (in `IosApp.kt`, over `StoreService.swift`) the
  only one that talks to StoreKit;
  `RemoveAdsManager` is the JVM-tested decision logic that keeps
  `data/AdsEntitlementRepository` (the device's copy of the entitlement) in step
  with what the store says — grant on purchase, revoke when the store answers
  with none, leave alone when it cannot be asked.
- **`location/`** — `LocationSource` is the seam: `LocationProvider` (app)
  over the platform `LocationManager` (coarse only, no Play Services, so it
  builds from source anywhere), `LocationService.swift` over CoreLocation on
  iOS.
  `LocationResolver` is the one answer to "where are we?": a saved place the
  user chose, else a live fix, else the last place we knew, else the built-in
  default. The background alert check shares it, so a chosen place is what
  background polling watches.
- **`widget/`** (app) — home screen widgets, Android only (deferred on iOS;
  docs/PARITY.md), each one tile of the glance.
  `WidgetConfig` is a `ViewConfig` with one visible module plus a
  `ThemeConfig`, so the glance's render, codecs and pickers drive it
  unchanged; `WidgetRefreshWorker` fetches once for every widget every 15
  minutes into a single `WidgetData` (own codec, `data/WidgetDataStore`);
  `WidgetContent` draws readings, the sun and the forecast in Glance
  (RemoteViews — `TextFit` estimates the value size the glance measures).
  Config and data are mirrored into Glance's per-widget state (`WidgetState`)
  because a live session recomposes without re-running `provideGlance`.
  `ui/widget/` (app) is the configure activity, built from the shared
  `ui/customize/Pickers`.
- **`data/places/`** — picking a place without a geocoder. `PlaceCatalog` is
  the pure parse + search over the bundled gazetteer
  (`app/src/main/assets/places.tsv`, built by `scripts/build-gazetteer.sh`
  from US Census and GeoNames data; `iosApp/project.yml` bundles the same
  file into the iOS app); `AssetPlaceSource` (shared/androidMain) and
  `BundlePlaceSource` (iosMain) are the only platform-aware parts; `SavedPlaces` + its codec
  and repository hold what the user kept and which one is showing.
- **`region/`** — a region is a Google Play country (on iOS, an App Store
  storefront country); it decides units, date order and clock, chosen
  automatically (Android: user's choice > phone network > last fix > place
  shown > language settings; iOS replaces the network with the storefront
  and adds the time zone last). `Storefronts.kt` maps the App Store's
  alpha-3 codes to the registry's alpha-2. The registry
  is `Regions.kt`. Everything about regions, including how to add one, is in
  [REGIONS.md](REGIONS.md).
- **`view/Conventions.kt`** — the one place a canonical value (°F, mph,
  inHg, in) becomes text in the user's units and date/clock style. Every
  formatter takes it; Compose reads it as `LocalConventions`.
- **`view/`** — the customization *data* (pure, no Compose): `WeatherField` (the
  data-point catalog), `ViewConfig` + `Density`, `ThemeConfig`, and their JSON
  codecs, plus `ModuleKey` (the catalog of things that can sit on the glance —
  every `WeatherField` via `ModuleKey.Reading`, plus `Sun`), `ModuleSize` (a
  tile's footprint in cells on the 4-column lattice, floored per module),
  `packGrid` (the pure lattice packing) and `packGridRows` (the flow-grid
  packing the forecast uses) and `ForecastMode` (the forecast grid's own
  framing). `ViewRender` turns a config
  + snapshot into the rendered module list, each module carrying a
  `ModuleContent` — a formatted reading, or richer data the tile draws itself.
  `ForecastElement` is what a forecast tile may show beside its temperature
  (the user's set lives on the config). `Details` builds what a tap on a tile opens (the whole observation behind a
  reading, every field of a forecast hour or day) as a pure `Detail` value;
  `ui/home/DetailSheet` only draws it.
- **`alerts/`** — personal alerting. `AlertRule` (subject + comparison +
  threshold + window), `AlertSubject` (a `WeatherField` or forecast-only
  `PrecipChance`), `AlertWindow` (now / forecast horizons / overnight). The pure
  core is `AlertEvaluator` and `AlertTransitions` (notify-once dedup) over a
  `WeatherContext`. `AlertCheck` is one background check — fetch, evaluate,
  dedupe, quiet hours, safety alerts — run by `AlertWorker` (app,
  WorkManager) on Android and by `AlertRefresh.swift` (`BGAppRefreshTask`)
  on iOS. `AlertNotifications` is the posting seam (`AlertNotifier` (app),
  `Notifier.swift`); `AlertSettings` holds quiet hours; `BackgroundAlerts`
  says how dependably the platform runs the check.
- **`ui/theme/`** — the palette + type scale and `JustMyWeatherTheme`, which maps
  a pure `ThemeConfig` to a Material color scheme + typography in one place.
- **`ui/home/`**, **`ui/customize/`**, **`ui/alerts/`** — one view model + one
  screen each. `ui/home/DensitySpec` maps a `Density` to concrete sizes/spacing.
  The home screen is **one arrangeable grid**: `ui/home/CellGrid` is the
  lattice engine (fixed cells; placements from `view/packGrid`),
  `ui/home/ModuleGrid` is the glance built on it — it owns all of arrange
  mode's gesture/animation machinery: drag to move, drag a corner to resize —
  and every module draws inside its tile, including `ui/home/ForecastModule`,
  the forecast with its own Hourly/Daily toggle in its header, whose inner
  hour/day tiles pack on `ui/home/TileGrid` (the flow-grid engine + the
  bordered tile shell) into exactly the module's columns. The criteria all of
  this answers to live in `docs/modular-v2-evaluation.md`.

## Freshness

Two different clocks meet on the glance, and conflating them is the most
common misreading of this app.

- **Observation time** (`WeatherSnapshot.observedAt`) — when a real thermometer
  at a real station took the reading. This is what the "Observed HH:MM" line
  shows, and it advances only when the station publishes.
- **Fetch time** — when the app last asked. Deliberately not displayed.
- **Observation age** (`ui/home/ObservationAge`) — the gap between the
  observation time and now, printed beside the timestamp ("· 12 min ago"). It
  is derived from the first clock, never the second, so it cannot make an old
  reading look fetched-just-now. `ObservedLine` re-reads the clock on a timer,
  because an age rendered once goes stale while the screen is open.

So the timestamp not changing across a Refresh is normal, not a stale-cache bug
— and the age beside it is what confirms the fetch happened at all.
`WeatherRepository` caches only the coordinate → grid/station resolution;
`getObservation` hits `/observations/latest` every time, and the NWS
transport has no HTTP cache on either platform (an `OkHttpClient` with none;
an ephemeral `NSURLSession` that ignores the local cache). The limits are upstream: station
cadence (5 minutes at KLOU/KSDF, hourly at many sites) and NWS's own
`max-age=183, s-maxage=300` on that endpoint.

The rule this encodes: **never substitute the current clock for a missing or
older observation time.** Doing so renders absent or stale data as freshly
observed. The same rule is why `Density` no longer hides the timestamp — a
number whose age is undiscoverable is what made the hero and the forecast strip
look like they were contradicting each other.

The one deliberate exception is the Gadgetbridge payload (Android only), which falls back to
`now` when a station omits its timestamp entirely: that field serialises to 0
otherwise, and a watch would render 1970 — worse than "about now" for a
consumer that keys freshness off it. It is commented as an exception at the
call site.

## Principles

- **Pure logic stays pure** so it tests on the JVM; side effects live at the
  edges. See `CONTRIBUTING.md`.
- **One seam per concern.** A new data source or cache is a change in one file.
- **Legibility is the spec** — this is meant to be forked. The common extension
  points each live in one obvious file; see `docs/extending.md`.
